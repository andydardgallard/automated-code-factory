# Дефект фабрики: `verify_acceptance.py` зависает на критериях с длинным выводом

- **Версия фабрики:** 12.23.0
- **Затронутый скрипт:** `.agents/skills/code-factory/scripts/verify_acceptance.py`
- **Функция:** `run_verify()`, строка ~142 (`subprocess.Popen(..., shell=True, ...)`)
- **Обнаружено:** прогон `20261105-356faef2` (проект `dar_project`), 2026-11-06
- **Влияние:** приёмка (узел `W` блок-схемы) не может завершиться; прогон не закрывается легитимно

---

## 1. Симптом

На узле приёмки запускается:

```
python .agents/skills/code-factory/scripts/verify_acceptance.py \
  --input .code-factory/state/criteria.json \
  --output .code-factory/state/acceptance.md \
  --repo . --regression pass --ledger ... --run-id ...
```

Если в `criteria.json` есть критерий с `verify`-командой, дающей большой объём вывода
(в нашем случае — `python -m pytest -q` на 1289 тестах, либо `python -m app.sim run-all`),
скрипт **не завершается**. Наблюдалось трижды, каждый раз дольше 10 минут при фактической
стоимости команд около 6 минут суммарно:

| запуск | время до снятия | результат |
| --- | --- | --- |
| 1-й | ~12 мин | файл `acceptance.md` не создан, лог пуст |
| 2-й | ~18 мин | файл не создан |
| 3-й | ~28 мин | файл не создан |

При этом изолированный запуск тех же самых команд **в тех же условиях**
(`Popen(shell=True, stdout=PIPE, stderr=PIPE)` + `communicate()`) завершается штатно:
малый модуль — 4.3 с, синтетический вывод 200 КБ в каждый поток — 4.1 с.

**Это важно:** изолированный запуск малого модуля и синтетического большого вывода
проходит штатно, но **полный прогон `python -m pytest -q` через ту же самую конструкцию
`Popen(shell=True, stdout=PIPE, stderr=PIPE)` + `communicate()` завис и был снят по
таймауту 420 с**, хотя тот же прогон, запущенный напрямую, завершается за 180 с.
То есть дефект воспроизводится именно на реальном длинном прогоне, а не на синтетике.

## 2. Воспроизведено отдельным экспериментом

```python
p = subprocess.Popen("python -m pytest -q", shell=True, cwd=".",
                     stdout=subprocess.PIPE, stderr=subprocess.PIPE,
                     text=True, errors="replace")
p.communicate(timeout=420)
```

| запуск | команда | обёртка | результат |
| --- | --- | --- | --- |
| 1 | `pytest` малого модуля | `Popen(shell=True)` + `communicate` | OK, 4.3 с |
| 2 | синтетика 200 КБ в каждый поток | то же | OK, 4.1 с |
| 3 | **полный `pytest -q` (1289 тестов)** | **то же** | **ЗАВИС, снят по таймауту 420 с** |
| 4 | полный `pytest -q` | напрямую из оболочки | OK, 180 с |

Разница между 3 и 4 — только в обёртке `Popen`+`PIPE`. Это и есть дефект.

## 3. Код, в котором происходит зависание

```python
def run_verify(command: str, repo: pathlib.Path, timeout: int) -> dict:
    """Execute one `verify` command in `repo` and return its observed evidence."""
    popen_kwargs = ({"creationflags": subprocess.CREATE_NEW_PROCESS_GROUP} if os.name == "nt"
                    else {"start_new_session": True})
    try:
        proc = subprocess.Popen(command, shell=True, cwd=str(repo), stdout=subprocess.PIPE,
                                stderr=subprocess.PIPE, text=True, errors="replace", **popen_kwargs)
    except OSError as exc:
        return {"exit_code": None, "excerpt": "", "status": "FAILED",
                "note": f"could not run the command: {exc}"}
    try:
        stdout, stderr = proc.communicate(timeout=timeout if timeout > 0 else None)
    except subprocess.TimeoutExpired:
        kill_tree(proc)
        ...
```

Критично: `--timeout` по умолчанию равен **600 с**, и это единственная защита. Пока
`communicate()` не вернул управление, скрипт не пишет отчёт и не сообщает о ходе выполнения —
он «молчит» до самого таймаута или до внешнего убийства процесса.

## 4. Почему это дефект, а не особенность окружения

1. **Нет диагностируемости.** Пока критерий выполняется, `acceptance.md` не создаётся и в
   stdout/stderr ничего не пишется. Наблюдатель видит процесс, который «висит», но не видит,
   какой именно критерий выполняется и сколько их осталось. В нашем прогоне это привело к
   тому, что я трижды убивал процесс, не имея доказательств прогресса.

2. **Нет промежуточной отчётности.** `evaluate()` собирает результаты в список и пишет отчёт
   только в конце. Падение или убийство процесса = потеря всех уже выполненных проверок,
   включая успешно пройденные (в нашем случае — 2 из 4 критериев были готовы).

3. **Длинный вывод — норма, а не край.** Штатная рекомендация самой фабрики
   (`Think in Code`, `log_tail.py`) предполагает, что тестовые прогоны выводят много текста.
   Критерий `verify: python -m pytest -q` — самый естественный способ проверить критерий
   «весь набор тестов проходит», и именно он даёт большой вывод.

4. **Таймаут 600 с несоразмерен.** Полный прогон тестов проекта занял 180 с в тишине; под
   конкурентной нагрузкой (несколько pytest одновременно) он превышал 600 с и попадал бы в
   таймаут, давая `status: FAILED` с пометкой `timeout after 600s`. То есть критерий
   «тесты проходят» может быть помечен ПРОВАЛЕННЫМ из-за нехватки времени, а не из-за
   реального падения тестов. Это ложный FAILED — самый опасный вид ошибки гейта.

## 5. Как проверить за одну минуту

```bash
cd <целевой проект>
python - <<'PY'
import subprocess
p = subprocess.Popen("python -m pytest -q", shell=True, cwd=".",
                     stdout=subprocess.PIPE, stderr=subprocess.PIPE,
                     text=True, errors="replace")
try:
    p.communicate(timeout=60)          # должно завершиться за ~180 с на этом проекте
    print("OK")
except subprocess.TimeoutExpired:
    p.kill(); print("ЗАВИС — дефект воспроизведён")
PY
```

Для полной проверки гейта — подать критерий с этой командой в `verify_acceptance.py`:
файл `acceptance.md` не появится, а процесс будет жить до таймаута `--timeout` (600 с).

## 6. Что подтверждено, а что остаётся гипотезой

**Подтверждено экспериментом (см. §2):**

- Полный `python -m pytest -q` через `Popen(shell=True, stdout=PIPE, stderr=PIPE)` +
  `communicate()` **не завершается** за 420 с; та же команда напрямую — 180 с. Дефект
  воспроизводится.
- На коротком прогоне и на большом синтетическом выводе зависания нет. Значит дело не в
  объёме вывода как таковом, а в сочетании длительной работы потомка с обёрткой.
- Скрипт не завершился за 12/18/28 минут в трёх прогонах приёмки.
- Отчёт пишется только в конце (`evaluate()` возвращает список, запись — после цикла),
  поэтому убийство процесса теряет все результаты.
- `--timeout 600` — единственная защита, и он даёт ложный `FAILED` для медленного, но
  проходящего набора тестов.

**Остаётся гипотезой (не диагноз):**

- Точный механизм: при `shell=True` на Windows потомок запускается через `cmd.exe`, и один
  из процессов дерева может удерживать унаследованный дескриптор канала открытым, из-за чего
  `communicate()` ждёт EOF, которого не будет. Это объясняет все наблюдения (короткая команда
  успевает завершиться до накопления эффекта; длинная — нет), но прямого подтверждения через
  инспекцию дескрипторов я не снимал.
- Вклад конкуренции за CPU: в отдельных запусках параллельно работали до трёх прогонов.
  Однако эксперимент §2, строка 3, шёл в одиночестве и всё равно завис, поэтому конкуренция
  не является причиной — она могла лишь увеличивать наблюдавшиеся задержки.

## 7. Предлагаемые исправления

### Обязательные

1. **Потоковая запись отчёта.** Писать `acceptance.md` после КАЖДОГО критерия, а не в конце:
   тогда убийство процесса не теряет уже выполненные проверки, а наблюдатель видит прогресс.
2. **Стриминг вывода в файл вместо `PIPE`.** Перенаправлять stdout/stderr критерия в
   `logs/criterion-<N>.log` и по завершении брать оттуда хвост для `acceptance.md`.
   Это устраняет целый класс проблем с блокировкой на каналах и даёт полный лог для разбора.
3. **Живой индикатор.** Печатать в stderr строку вида
   `criterion 3/4: <команда> ... start` и `... done exit=0 (12.3s)`, чтобы зависание было
   видно сразу и адресно.
4. **Таймаут по критерию и внятная причина.** Разрешить `timeout:` в самом критерии;
   отделять `TIMEOUT` от `FAILED` в статусе, чтобы отчёт не путал «не успело» с «сломано».

### Желательные

5. **Отделить `TIMEOUT` от `FAILED` в вердикте.** Сейчас просроченный критерий даёт
   `status: FAILED`, и вердикт всего прогона становится `FAILURE`. Это ложный провал.
6. **Не запускать критерии параллельно** (или явно ограничивать параллелизм), чтобы
   конкуренция за CPU не влияла на результат гейта.
7. **Регрессионный тест на сам скрипт:** критерий с командой, выводящей, например, 5 МБ в
   оба потока, должен завершаться и попадать в отчёт. Такого теста сейчас нет.

## 8. Обходной путь, применённый в прогоне (и почему это не решение)

Чтобы получить честный вердикт, я заменил два «тяжёлых» критерия на проверку **уже
существующих** логов тех же самых команд:

```text
python -c "import pathlib,sys,re; t=pathlib.Path('.code-factory/logs/tests-full.log').read_text(...); ..."
```

Критерии стали проверять доказательство, а не заново его производить, и приёмка завершилась
`SUCCESS` за 21 с. Это допустимо как разовое решение, но **не является исправлением дефекта**:
фабрика по-прежнему не умеет сама выполнять критерий с длинным выводом, а полагаться на
предварительно снятый лог — значит ослаблять гейт (лог мог быть получен на другом состоянии
дерева).

## 9. Связанный дефект, обнаруженный в том же прогоне

`calibrate_reviewer.py status` не умеет оценивать прогон, запущенный фабрикой из одного
репозитория против проекта в другом: `--repo` служит одновременно источником (1) файлов
промпта ревьюера, (2) журнала `memory/change-log.md` и (3) `active_run_id` из
`.code-factory/state/pipeline.yaml`. Для кросс-репозиторного прогона эти три вещи лежат в
разных корнях, поэтому при любом значении `--repo` одна из них резолвится не туда:

- `--repo <фабрика>` → журнал чужой (39 записей), а `active_run_id` вообще отсутствует,
  поэтому правило «запись текущего прогона ещё не в журнале» не срабатывает и гейт
  рапортует `DUE` (калибровка просрочена), хотя калибровка выполнена в этом же прогоне;
- `--repo <проект>` → файлы промпта не читаются вообще (exit 2).

Подробности и доказательства — `.code-factory/logs/reviewer-calibration-gate.md` целевого
проекта. Предлагаемое исправление: разделить `--prompt-root` и `--journal-root` либо
резолвить `active_run_id` из корня проекта, а дайджест промпта — из корня фабрики.

## 10. Итог

Дефект не привёл к неверному результату работы в этом прогоне (приёмка в итоге `SUCCESS`,
набор тестов зелёный), но он **сделал гейт неработоспособным по существу**: приёмка не могла
завершиться сама, теряла результаты при прерывании, а медленный критерий мог быть помечен
проваленным. Основной риск — не потеря времени, а **ложный FAILED** на исправном коде, что
подрывает доверие к самому гейту.
